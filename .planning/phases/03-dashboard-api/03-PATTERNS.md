## Pattern Assignments

### `iris/PopHeat/<REST class>.cls` (route/controller, request-response)

**Analog:** `iris/PopHeat/BatchTelemetry.cls` (embedded-SQL query convention) + `iris/PopHeat/Reading.cls` (schema/field names + doc-comment style)

**Class/property doc-comment convention** (`iris/PopHeat/Reading.cls` lines 1-27):
```objectscript
Class PopHeat.Reading Extends %Persistent
{

/// OSM-derived venue identifier, e.g. "node/1223740137" (INGE-06).
Property VenueId As %String(MAXLEN = 255);
...
Property Latitude As %Double;
Property Longitude As %Double;
Property Popularity As %Numeric(SCALE = 3);
Property HeatLevel As %String(MAXLEN = 20);
Property ObservedAt As %TimeStamp;
```
Every class/property in this codebase carries a `///` doc comment citing the requirement ID it satisfies (e.g. `(INGE-06)`, `(HEAT-01)`) — the new REST class and its methods should follow the same convention, citing `DASH-0x` / `R1`-`R7` / `D-0x` IDs from `specs/dashboard-api.spec` and `03-CONTEXT.md`.

**Embedded-SQL query pattern to copy for "latest reading per venue" (D-04)** (`iris/PopHeat/BatchTelemetry.cls` lines 20-28):
```objectscript
/// Operational visibility into the most recent batches only (TELE-05):
/// the latest 20 telemetry rows, newest first -- never the full
/// historical log, so throughput reporting reflects current behavior.
Query RecentBatches() As %SQLQuery(CONTAINID = 1)
{
SELECT TOP 20 ID, ReadingCount, ElapsedSeconds, Throughput, RecordedAt
FROM PopHeat.BatchTelemetry
ORDER BY RecordedAt DESC
}
```
This is the direct analog for two of the REST endpoints:
- **Telemetry endpoint**: wrap/re-expose this exact query (D-decision in `03-CONTEXT.md`: "this phase's telemetry endpoint can query or wrap this directly rather than re-deriving the 'recent 20' logic"). Do not re-derive TOP-20 logic in the REST class — call `##class(PopHeat.BatchTelemetry).RecentBatchesFunc()` (generated by the `%SQLQuery`) or run the equivalent embedded SQL directly.
- **Latest-reading-per-venue endpoint** (D-04, R1/R5 — single source of truth for the map AND the counts): follow the same `%SQLQuery`-on-a-Persistent-class shape, but grouped, e.g.:
```objectscript
Query LatestPerVenue() As %SQLQuery
{
SELECT r.VenueId, r.VenueName, r.Category, r.Latitude, r.Longitude,
       r.Popularity, r.HeatLevel, r.ObservedAt
FROM PopHeat.Reading r
INNER JOIN (
  SELECT VenueId, MAX(ObservedAt) AS MaxObservedAt
  FROM PopHeat.Reading
  GROUP BY VenueId
) latest ON r.VenueId = latest.VenueId AND r.ObservedAt = latest.MaxObservedAt
}
```
This single query backs both DASH-01 (map data) and DASH-05 (heat-level counts, via a `GROUP BY HeatLevel` aggregation over the same result set or a second query built the same way) — per D-04's "never drift apart" requirement, do not write two separately-derived queries.

**Field names to expose verbatim (do not rename)** — fixed by Phase 2, confirmed in `popheat_pipeline/components.py` lines 255-262 and 279-282:
- Reading: `VenueId`, `VenueName`, `Category`, `Latitude`, `Longitude`, `Popularity`, `HeatLevel`, `ObservedAt`
- BatchTelemetry: `ReadingCount`, `ElapsedSeconds`, `Throughput`, `RecordedAt`

**Status endpoint pattern (D-06)** — no analog in repo; use directly per `03-CONTEXT.md` D-06:
```objectscript
Set isRunning = ##class(Ens.Director).IsProductionRunning("PopHeat.Production")
```
Wrap in try/catch so a failed check degrades to "Stopped" rather than erroring the whole response (UI-SPEC backstop: "Status badge falls back to 'Pipeline: Stopped' ... rather than blank/crashing").

**No error-handling / auth precedent exists** in `Reading.cls`/`BatchTelemetry.cls` (they are plain persistent data classes with no methods). The REST class must establish its own conventions:
- Auth: none — dashboard is public/no-login (per UI-SPEC "no form submission, no login").
- Error handling: wrap each REST method body in `try/catch`, return HTTP 200 with a JSON error body (or empty array) on internal query failure — because D-07's client-side stale-banner behavior depends on receiving *some* response to distinguish "fetch failed" (network/HTTP error) from "fetch succeeded but empty" (empty-state, per UI-SPEC). Prefer surfacing a non-200 status on genuine query failure so the client's `fetch` catch path (D-07 banner) triggers correctly; do not silently return `200 []` for real errors, that would be mistaken for the legitimate empty-state (UI-SPEC "No readings yet").

### `iris/PopHeat/dashboard.csp` (component, static page)

**Analog:** none in repo — greenfield. Build directly from `03-UI-SPEC.md`'s locked contract:
- Single static HTML file, vanilla JS, Leaflet + Leaflet.heat from CDN (no build step, D-05).
- Fixed 56px top bar (title + status badge) + full-bleed map below (UI-SPEC "Layout dimensions").
- `setInterval(..., 10000)` poll of the REST API (D-08), each cycle fetching venues/counts/telemetry/status and re-rendering; on fetch failure, show the dismissible banner with last-successful-fetch timestamp and leave prior DOM state untouched (D-07) rather than clearing it.
- Color/typography/spacing tokens: copy verbatim from `03-UI-SPEC.md` (`#F5F6F8` background, `#1F2933` chrome, `#3B82F6` accent, `#DC2626` error, heat gradient `#2ECC71/#F1C40F/#E67E22/#E74C3C`; type scale 16/13/20/28px; spacing 4/8/16/24/32px).
- Heat-layer min-weight: `Math.max(popularity, 0.15)` (UI-SPEC pinned default).
- Marker radii: CRITICO 14px, ALTO 10px, both `L.circleMarker` with 1px white stroke (UI-SPEC pinned default).

## Shared Patterns

### Requirement-ID doc comments
**Source:** `iris/PopHeat/Reading.cls`, `iris/PopHeat/BatchTelemetry.cls` (every `///` comment)
**Apply to:** All new/modified ObjectScript in this phase
```objectscript
/// <one-line description> (DASH-0x / R1-R7 / D-0x).
```

### Insert-only / read-only data discipline
**Source:** `iris/PopHeat/Reading.cls` line 29-31 comment ("insert-only... Do not add UPDATE/DELETE logic")
**Apply to:** The REST class — it must only ever `SELECT` from `PopHeat.Reading`/`PopHeat.BatchTelemetry`, never write, per `03-CONTEXT.md` "Integration Points: this phase reads Phase 2's tables; it writes nothing back to them."

### Single-container/single-namespace discipline
**Source:** `docker-compose.yml` (Phase 2, referenced in `03-CONTEXT.md` D-03) — no separate analog file needed, just the constraint
**Apply to:** REST class and CSP page — both must be compiled/served from the existing `POPHEAT` namespace/container; no new container, no new service.

### Imperative fallback for merge.cpf gaps
**Source:** `docker/init-production.sh` lines 17-33 (the `NS_EXISTS` check + imperative `Config.Namespaces`/`Config.Databases` creation when the declarative merge.cpf action doesn't take effect)
**Apply to:** Any new config work in `merge.cpf`/`init-production.sh` needed to expose the REST dispatch class and static CSP page as web applications.
