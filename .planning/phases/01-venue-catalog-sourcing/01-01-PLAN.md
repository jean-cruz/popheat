<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Internet (overpass-api.de) -> build_catalog.py | Untrusted response data crosses here — arbitrary JSON from a public third-party API, no schema contract enforced by the server |
| build_catalog.py -> local filesystem | Script writes JSON files (data/venues.json, data/venues.raw.json) derived from that untrusted external data |
| config/catalog_build.json -> build_catalog.py | Local, developer-controlled input that shapes the outbound query |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-01-01 | Tampering | Overpass JSON response parsing | high | mitigate | Strict `json.loads` only (no `eval`/`exec`); malformed JSON or a response missing `elements` raises `OverpassFetchError` and aborts the write path — never partially trusted. |
| T-01-02 | Denial of Service | HTTP call to overpass-api.de | high | mitigate | `urllib.request.urlopen(..., timeout=request_timeout_seconds)` client-side timeout PLUS an Overpass `[timeout:overpass_timeout_seconds]` server-side hint; response read is capped at `max_response_bytes` before `json.loads` is attempted, raising `OverpassFetchError` on overflow — an oversized or hanging response can never exhaust memory or block indefinitely. |
| T-01-03 | Tampering (unsafe/partial write) | Local writes to data/venues.json, data/venues.raw.json | high | mitigate | `write_json_atomic` always writes to a `tempfile.NamedTemporaryFile` in the target directory then `os.replace()`s it onto the final path; output paths are hardcoded constants (`CATALOG_PATH`, `RAW_SNAPSHOT_PATH`), never built from Overpass- or config-controlled dynamic strings, so no external input can influence the write target. |
| T-01-04 | Information Disclosure | Overpass response -> generated catalog | medium | mitigate | `map_element_to_venue` copies ONLY the 5 whitelisted fields (id/name/category/lat/lon); OSM contributor metadata (`user`, `uid`, `changeset`) and unrelated tags (`contact:*`, etc.) are never copied into the output — enforced by `must_haves.prohibitions` item 1 and its unit test. |
| T-01-05 | Tampering (injection via unsanitized strings) | venue name/category strings -> data/venues.json -> eventual Phase-3 dashboard display | medium | mitigate | Values are stored as opaque JSON strings via standard `json.dump` (which escapes control characters); no string concatenation into HTML/SQL/shell occurs anywhere in this phase's code. Phase 3's dashboard is responsible for rendering these values as text, never `innerHTML` — out of this phase's scope but noted for continuity. |
| T-01-06 | Spoofing | overpass-api.de endpoint identity | low | accept | HTTPS to a fixed hardcoded hostname with default Python TLS certificate validation; no certificate pinning. Acceptable for a public, unauthenticated, read-only geodata query — a spoofed response degrades to a build-time data-quality failure, not a security compromise, and D-05's fail-loud posture already limits blast radius. |
| T-01-07 | Tampering | config/catalog_build.json parsing | low | accept | Config is authored and controlled solely by the developer; no external/multi-tenant write path exists for this file. Malformed values are caught by `load_config`'s explicit validation (fail loud, non-zero exit) rather than silently accepted. |
| T-01-08 | Denial of Service (availability) | Single overpass-api.de endpoint, no mirror | low | accept | D-04 explicitly chose single-endpoint-only for v1 simplicity. If overpass-api.de is unreachable the build fails loudly (D-05) and Phase 2's pipeline continues on the last known-good catalog — an accepted availability tradeoff per explicit user decision, not a vulnerability. |
</threat_model>
